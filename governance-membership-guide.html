About the membership tool

A working reference for shaping who sits on each governance group — comparing views fairly, suggesting then confirming list changes, keeping a manageable timeline of composition, and exporting clean lists (including point-in-time PDFs) when needed. This page explains every part of the tool so colleagues can use it confidently and suggest improvements.

Open the tool: Membership tool
Related: Governance overview

What this tool is for

Formal meeting packs and decisions still live in SharePoint and with the Project Manager / Project Owner. This portal tool is the shared working list: who people think belongs on each group, how strong that consensus is, and how membership has changed over time — without turning opinions into a public vote trail.

Why it exists

Membership for Board, Steering, Technical, Business, and any extra working sets is still being formed.

Different people bring different knowledge of roles and remits. Signed-in colleagues can optionally mark Yes, Maybe, or No for each person on each group — shared tallies show where views align. Moving people between lists is normal: most people suggest changes; confirmers (Lisa / William) accept those suggestions onto the live lists and can set whether a group is Active or still In development.

As groups move from forming to stable — and later as people join, leave, or change roles — the tool keeps a continuous history so you can look back and see exactly who was on each list at a point in time.

What you see on the page

The membership tool is a two-column workbench on wider screens. Open the tool.

Left sidebar

  • Quick jumps — Add someone, Add a group, History
  • How to use — short reminder list (this guide is the full version)
  • Add someone — name + job title + starting group
  • Create a new group — custom working set beyond the core four

Main column

  • Groups jump bar — each group, Unassigned, History
  • Toolbar — Export PDF / CSV / JSON and Clear my marks
  • Group panels — roster chips, then member rows
  • Unassigned pool — people not yet on any group
  • Group history — paged timeline (Milestones, status focus, name search, snapshot PDF)

Your marks and tallies

Each signed-in person can optionally mark Yes / Maybe / No for each person on each group. Marks are never required when someone is moved. Try it on any group panel.

  • Your mark is private and optional by default. The API and exports do not list who voted what — only you see your own buttons as selected, unless you choose to share a reason (see below).
  • Reason (optional) — after you mark Yes / Maybe / No, add a short note explaining why. Tick Share with others so colleagues see your name, note, and mark under that person; leave it unticked to keep the note private. Existing notes stay private until you opt in.
  • Tallies are always shared: counts of Yes, Maybe, and No for that person on that list.
  • One mark per person per group — changing your mind overwrites your previous mark for that pair.
  • Clear my marks (toolbar or per group) removes only your opinions. Other people’s marks and the membership lists stay put.
  • Within a group, people with more Yes tend to float higher in the member list (with manual order as a tie-break).

Moving people and building lists

Membership (who is on which list) is shared. Opinions sit on top of that. List changes follow suggest → confirm unless you are a membership confirmer (Lisa / William).

  • Roster under each group heading is the quick “who’s on this list” scan — chip links jump to the member row. Tentative suggestions appear with distinct badges / dashed chips until accepted.
  • Person types — attributes appear as badges; use Filter by person type to narrow lists.
  • Manage types — confirmers use Person types in the sidebar to create custom types, rename any type, or delete a custom type. On each person, open Edit types to tick or clear types and Save.
  • Also on / Move to — under Place on another group (or Suggest place… if you are not a confirmer). Multi-membership is allowed for “also on”. Moving people is normal — no one is asked to “assess” a placement afterwards.
  • × Remove — confirmers remove from this group immediately; everyone else sends a suggested removal (the person stays on the list, struck through, until Accept / Reject).
  • Accept / Reject — confirmers decide on pending suggestions; the proposer can withdraw their own suggestion.
  • Unassigned pool — people with no group yet; use Add (or suggest Add) to place them.
  • Add someone — creates a person with name and job title only and places them on a group. Prefer name and role only — no emails.

Core groups, custom groups, and status

Not every list is at the same stage of life.

The four core groups are always present: Project Board, Steering Group, Technical Group, and Business Group. You can also create a custom group for a temporary or specialist working set. Custom groups can be deleted; the core four cannot.

Each group has a lifecycle status (independent of the others) — set on the group panel in the tool (membership confirmers only):

  • In development — still being shaped (default for new groups)
  • Active / stable — formed and expected to hold steady, with joiners/leavers over time
  • Inactive — paused or not currently meeting
  • Dissolved — closed; kept for history rather than day-to-day use

Status badges are visible to everyone. Changing status is confirmer only (Lisa / William today). A group can be Active for a while and later go back to In development — that does not stop anyone else from suggesting membership changes. Status changes are recorded in history. See an example on the Project Board panel.

Group history and checkpoints

A continuous timeline of membership composition — not of private opinions. Built to stay usable as the log grows. Open Group history in the tool.

  • Every meaningful membership change (add/move/remove person, create/delete group, reorder save, status change) can write a JSON snapshot of who sat where, with name and role as they were then.
  • Identical consecutive snapshots are skipped so the timeline stays readable.
  • The first time history is empty, a starting baseline is pinned automatically.
  • Save checkpoint pins a milestone even if the lists have not changed — useful when a group is formally confirmed.
  • Click any timeline entry to see a read-only view of all groups at that moment (including their status if recorded).
  • The timeline does not dump every row at once: it loads in pages (with a count and Show older), and Milestones filters to checkpoints and the starting baseline so hundreds of routine changes stay manageable.
  • Focus the open snapshot by lifecycle status (e.g. Active / stable only) or search by person or group name — the view and the snapshot PDF follow that focus.
  • From a selected snapshot card (“As of … · reason · by …”), Export PDF produces the same formal membership document as the live export, dated to that point in time.
  • Restore this composition (confirmers) replaces the live lists with that snapshot — use after a mistaken change. Reseed unassigned restores seed-file groups only for people who currently have no placement.

Exports (PDF, CSV, JSON)

For packs, spreadsheets, and backups — without leaking private marks. Controls live in the toolbar.

  • Export PDF — formal “as of” membership document: name, role, and other groups; suitable for meeting packs. The same style is available from any history snapshot card (respecting status / search focus).
  • Export Excel / CSV — tabular membership for Excel or SharePoint lists. Tallies may appear as counts; who marked what does not.
  • Export JSON — machine-readable dump of the current working state for reference or analysis. The live database remains the source of truth (there is no import back into the tool).

Privacy and data rules

Deliberately light personal data — enough for coordination, nothing more.

  • Record name and job title / role only. Do not enter email addresses, phone numbers, or other personal details.
  • Individual Yes / Maybe / No marks stay anonymous in tallies and exports. Reasons you mark as shared appear with your name (and mark) under that person for other signed-in users; private reasons stay visible only to you.
  • History stores composition (and group status), not who thought what.
  • The portal is an internal working site (noindex) — not a public directory of staff.

Who can do what

You must be signed in through the portal to use the tool.

  • Signed-in users — mark Yes / Maybe / No; add an optional reason (shared or private); see tallies and shared reasons; clear their own marks; export live lists; browse history (paged / Milestones); focus a snapshot by status or search; export a snapshot PDF; suggest add / move / remove (tentative until confirmed); withdraw their own suggestions.
  • Membership confirmers (Lisa / William as administrators today) — everything above, plus Accept / Reject suggestions, make live add / move / remove changes, create or delete custom groups, set lifecycle status, and save checkpoints.
  • Not signed in — the tool will not load live data; sign in via the PHP portal.

What this tool is not

  • Not a substitute for the Governance overview (remits, cadence, and how groups relate).
  • Not a place for confidential HR or personal case information.
  • Not a voting system that binds the programme — tallies inform shaping; confirmation sits elsewhere.

Where this could go next

Captured as a direction of travel — not built yet.

A membership tool any project manager could use

Today this instance is fixed to Housing Digital Transformation governance. The same pattern — named people, opinions with optional marks and shareable reasons, group lifecycle status, and a continuous membership history — would be powerful as a multi-project tool across the council (or beyond).

In that shape, a project manager would:

  • Name their project — each project is a separate workspace, not a shared single list.
  • Define teams / groups inside it — Board, Steering, workstreams, or whatever the remits need; labels are project-owned.
  • Give each group its own purpose — remit, memorandum, or short purpose text that can differ even when two projects use the same group name.
  • Reuse people across projects — the same person can sit on “Steering” in Project A and Project B with different roles, marks, and history in each.
  • Keep history and status per project — forming → active → inactive / dissolved stays local to that project’s groups.

The point is reuse of the method, not one global membership directory: many projects, many teams, possibly the same names and people, but different remits, purposes, and timelines. Building that is a later piece of work; this page exists so the idea is written down and open to challenge or refinement.

What is already live vs still to come

  • Live now — suggest → confirm for add / move / remove; tentative styling; Accept / Reject / withdraw; group lifecycle status; paged history with Milestones; snapshot status focus and name search; checkpoint pins; PDF from the live list or from a history snapshot.
  • Still to come — allocate the Project Owner (e.g. Lisa) or other group administrators as confirmers for particular lists, without handing them every group; multi-project workspaces (above).

Suggest an improvement

This tool will keep evolving as groups form and settle — including multi-project workspaces and wider confirmer allocation above.
