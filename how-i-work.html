A working reference for how research, AI tools, engineering choices, and Microsoft 365 fit together day to day

William Ellis Digital Transformation Lead
1

Research & Content Generation

⏱ ~5 minutes

I use AI research tools to turn source material into whatever format actually gets read by the audience I'm writing for — not everything needs to be a document.

Google NotebookLM My main research workhorse. I load source material in and generate research summaries, explainer videos, infographics, presentations, and podcast-style audio overviews from the same source set.
Google Stitch Google's AI UI/design tool — useful for quickly generating interface concepts and visual directions before committing engineering time to a design.
Why this matters: a stakeholder briefing, a five-minute video, and an infographic all come from the same underlying research — the format changes to fit the audience, not the substance.
2

AI-Assisted Development

⏱ ~5 minutes

Editor & Assistants

  • Cursor — my primary editor, AI-native from the ground up
  • Claude — for reasoning through design decisions, writing, and review
  • Claude Desktop — for work that sits outside a codebase entirely
  • Claude in Cursor — Claude working directly inside the editor, with full repo context, so it can read, plan, and edit across a whole project rather than one file at a time

Local Models

  • Ollama — runs models entirely on my own machine, no data leaving it
  • Models pulled and kept current from Hugging Face and LM Studio
  • Used where I want a task done fully offline, or want to compare a local model's output against a hosted one
Principle: the right tool depends on the task — a hosted frontier model for hard reasoning, a local model when privacy or offline access matters more than raw capability.
3

Technology Philosophy

⏱ ~5 minutes

Current vs. Preferred Stack

  • PHP / MySQL is what I deliver in today — it matches existing hosting and skills, and it ships reliably
  • SvelteKit, paired with whichever database actually fits the job rather than one default choice, is my preference where I have a free hand
  • The deciding factor is always what the environment can actually support and maintain, not personal preference alone

Functional Over Object-Oriented

  • I default to functional programming over OOP
  • In a social organisation like a council, OOP's inheritance and shared mutable state tend to accumulate hidden coupling as teams and requirements change — functional code with clear inputs and outputs stays easier to reason about as ownership shifts
  • I draw on Category theory and Set theory as the underlying mental model for how data and transformations compose
JSON everywhere: I use JSON as the default interchange format across systems — it's simple, language-agnostic, and keeps interoperability straightforward as tools and teams change.
4

Guiding Principles

⏱ ~5 minutes
“Information as a System” — every tool and dataset I build is a piece of one connected picture, not a one-off, so the effort compounds instead of fragmenting.
Reduce Duplication
One authoritative source of a given fact, referenced everywhere else — not re-typed and re-diverging
Improve Standardisation
Consistent structures and formats so systems can talk to each other without bespoke translation every time
User Wellbeing
Standardisation isn't the end goal — it's what frees up time and headspace for the people using and maintaining the system
Accessibility (A11y): treated as a baseline requirement, not a late-stage compliance check — every tool I build needs to work for everyone using it, from the first version.
